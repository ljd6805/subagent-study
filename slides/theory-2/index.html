Part 1

병렬 실행

자식 여러 명을 한 번에 띄우는 것은 쉽다. 어려운 것은 무엇을 나눌지와 돌아온 결과를 어떻게 합칠지다.

1한 응답, 여러 호출2독립성 판단3시간과 토큰4결과 모으기5두 가지 상한6쪼개는 방식
Parallel 1 · Fan-out

병렬 실행은 한 응답에서 위임 도구를 여러 번 부르는 것이다

TRY"세 관점으로 동시에 검토해 줘"처럼 독립된 일 세 개를 한 번에 요청하고, 자식 실행이 겹쳐서 시작되는지 기록을 보자.
Parallel 2 · Independence

병렬은 일이 서로 독립적일 때만 이득이다

질문 1 · 입력
앞 결과가 필요한가?

B가 A의 결과를 보고 시작해야 한다면 동시에 띄울 수 없다. 억지로 띄우면 B는 추측으로 일한다.

질문 2 · 쓰기
같은 것을 고치나?

같은 파일, 같은 설정, 같은 DB를 고친다면 나중에 쓴 쪽이 앞의 변경을 덮는다. (Part 3)

질문 3 · 합치기
합치는 규칙이 있나?

결과가 서로 다르게 나오면 무엇을 믿을지 미리 정해 두지 않으면, 부모가 결과 앞에서 다시 조사를 시작한다.

병렬에 맞는 일
  • 모듈별 코드 탐색 (읽기만 한다)
  • 보안 · 성능 · 테스트 관점별 리뷰
  • 원인 가설 여러 개를 따로 검증
  • 서로 다른 파일을 각자 맡는 작업
병렬이 손해인 일
  • 조사 결과를 보고 수정 범위를 정하는 일
  • 한 파일을 여러 곳에서 고치는 리팩터링
  • 순서가 있는 마이그레이션
  • 자식 하나로 몇 초면 끝나는 작은 일
TRY지금 하고 있는 작업을 세 조각으로 나눠 보고, 세 질문에 모두 "아니오 · 아니오 · 예"가 나오는지 확인해 보자.
Parallel 3 · Cost

병렬로 얻는 것은 시간이고, 치르는 것은 토큰과 조율이다

기본 비용

자식은 시스템 프롬프트, 프로젝트 지침, 도구 설명을 각자 처음부터 읽는다. 자식 수만큼 늘어난다.

겹치는 탐색

범위를 나눠 줘도 자식들이 같은 공통 파일을 각자 읽는다. 브리프에 이미 아는 것을 적어 줄수록 줄어든다.

모으는 비용

부모는 보고 N개를 읽고 합친다. 보고가 길면 부모 컨텍스트가 다시 커진다.

TRY같은 일을 자식 하나로 한 번, 셋으로 한 번 돌려서 총 토큰과 걸린 시간을 나란히 적어 보자.
Parallel 4 · Gather

병렬의 품질은 결과를 모으는 단계에서 정해진다

① 같은 모양으로 받기

모든 자식에게 같은 반환 형식을 준다. 결론 · 근거 · 미확인처럼 칸이 같아야 부모가 줄 맞춰 비교할 수 있다.

② 큰 결과는 파일로

자식마다 다른 파일 이름에 자세한 내용을 쓰고, 부모에게는 요약과 경로만 돌려준다. 이름이 겹치면 서로 덮어쓴다.

③ 충돌 규칙 미리 정하기

둘이 다른 결론을 내면? "재현 테스트가 있는 쪽을 믿는다"처럼 판정 기준을 브리프에 적어 둔다.

brief · 반환 형식 예시# 세 자식에게 똑같이 붙이는 부분
반환 형식:
  결론: 한 줄
  근거: 파일:줄 목록 (최대 5개)
  미확인: 확인 못 한 것
  상세: reports/{관점}.md 에 기록

판정 기준:
  재현 테스트가 있는 지적을 우선한다.
  같은 줄을 둘 이상이 지적하면 하나로 합친다.

# 부모가 받는 것
security: 결론 · 근거 3 · reports/security.md
perf    : 결론 · 근거 2 · reports/perf.md
tests   : 결론 · 근거 4 · reports/tests.md
TRY반환 형식을 주지 않고 한 번, 위처럼 주고 한 번 병렬로 돌려 보자. 부모가 결과를 합치는 데 쓴 턴 수가 어떻게 달라지는지 보자.
Parallel 5 · Limits

동시 실행 상한과 깊이 상한은 자식 수가 끝없이 늘어나는 것을 막는다

동시 실행 상한
한꺼번에 몇 명까지

넘는 요청은 순서를 기다리거나 거절된다. 비용과 API 속도 제한을 지키는 설정이다.

깊이 상한
자식이 또 자식을

중첩 위임을 몇 단계까지 허용할지 정한다. 대부분 기본값은 얕게 잡혀 있다.

깊이를 늘리기 전에, 부모가 직접 폭으로 나눌 수 있는지 먼저 본다. 깊은 위임은 브리프가 단계마다 흐려진다.
TRY쓰는 도구의 동시 실행 상한과 깊이 상한 기본값을 Appendix에서 찾아 적어 두자.
Parallel 6 · Decomposition

무엇을 기준으로 쪼개느냐가 결과의 모양을 정한다

영역별
파일 · 모듈

각자 다른 디렉터리를 맡는다. 쓰기 충돌이 적고 합치기도 쉽다.

예: api/ · web/ · db/ 를 각각 탐색

관점별
같은 대상, 다른 기준

같은 코드를 보안 · 성능 · 테스트 기준으로 따로 본다. 한 명이 한 종류만 보게 해 빠뜨림을 줄인다.

예: PR 하나를 세 관점으로 리뷰

가설별
원인 후보마다

버그 원인 후보마다 한 명씩 붙여 검증한다. 처음 찾은 그럴듯한 설명에 매달리는 것을 막는다.

예: 캐시 · 동시성 · 설정 가설

후보별
같은 일, 다른 방법

같은 문제를 다른 방법으로 각자 풀게 하고 부모가 비교해서 고른다. 비용이 가장 크다.

예: 구현안 A · B 비교

영역별로 쪼갤 때는 쓰기 충돌을, 관점별 · 가설별로 쪼갤 때는 결과 합치기를, 후보별로 쪼갤 때는 비용을 먼저 따진다.
TRY같은 리뷰 작업을 영역별 · 관점별로 각각 쪼개 돌려 보고, 어느 쪽이 빠뜨린 지적이 적은지 비교해 보자.

Part 2

백그라운드 실행

자식이 끝날 때까지 기다리지 않는다. 부모는 작업 ID만 먼저 받고 다른 일을 하다가, 결과는 나중에 알림으로 받는다.

1기다림 없는 위임2나중에 오는 결과3권한 요청4실행 중 관리5언제 쓰나6같은 폴더 문제
Background 1 · Don't wait

포그라운드 위임은 결과를 기다리고,
백그라운드 위임은 작업 ID만 받고 바로 돌아온다

TRY긴 테스트 실행을 백그라운드로 맡긴 뒤, 부모가 결과를 받기 전에 무슨 판단을 했는지 기록에서 확인해 보자.
Background 2 · Late result

결과는 부모 대화에 나중에 끼어드는 메시지로 들어온다

도착 방식

자식이 끝나면 하네스가 완료 알림을 만들어 부모의 다음 입력에 넣는다. 부모가 따로 물어보지 않아도 된다.

문제 1 · 낡은 결과

자식이 조사하는 동안 부모가 파일을 바꿨다면, 돌아온 결과는 바뀌기 전 코드에 대한 것이다.

문제 2 · 엇갈린 판단

부모가 자식 결과를 예상해서 먼저 진행했는데 결과가 반대로 오면, 이미 한 일을 되돌려야 한다.

부모 대화 기록의 모습 (예시)user   테스트 돌려 놓고 README도 고쳐 줘
parent delegate(test-runner, background)
result 시작함 · id=t-17
parent edit(README.md) …
parent README 수정 끝났습니다.

── 완료 알림 ─────────────
t-17 done: 실패 2건
  test_cart.py::test_total
  test_cart.py::test_discount

parent 테스트 결과가 도착했습니다.
       실패 2건을 보겠습니다 …
알림을 받으면 부모는 먼저 "그 사이에 무엇이 바뀌었나"를 확인해야 한다. 브리프에 "작업 시작 시점의 커밋"을 적게 하면 판단이 쉬워진다.
TRY백그라운드 자식이 도는 동안 부모에게 같은 파일을 고치게 해 보고, 돌아온 결과가 최신 코드와 맞는지 확인해 보자.
Background 3 · Permissions

백그라운드 자식은 사용자에게 바로 물어볼 수 없다

포그라운드
물으면 사용자가 본다

자식이 위험한 명령을 실행하려 하면 승인 요청이 화면에 뜨고, 사용자가 그 자리에서 답한다.

백그라운드
물을 곳이 마땅치 않다

사용자는 부모와 다른 이야기를 하는 중이다. 승인 요청은 미뤄지거나, 거절되거나, 부모 화면에 끼어든다. 어느 쪽이든 자식은 멈춘다.

설계 방법내용맞는 일
읽기 전용으로 돌린다쓰기 · 실행 도구를 빼서 애초에 승인이 필요 없게 한다탐색, 리뷰, 조사
미리 허용해 둔다필요한 명령만 허용 목록에 넣고 나머지는 자동 거절한다정해진 테스트 · 빌드 실행
시작 전에 묻는다띄우기 전에 필요한 권한을 한꺼번에 확인받는다파일을 고치는 긴 작업
거절되면 보고한다막힌 지점을 결과에 적고 끝낸다. 부모가 이어서 처리한다범위가 불확실한 작업
TRY허용되지 않은 명령이 필요한 일을 백그라운드로 맡겨 보고, 승인 요청이 어디에 어떻게 나타나는지 확인해 보자.
Background 4 · Manage

돌고 있는 자식은 들여다보고, 이어서 지시하고, 멈출 수 있어야 한다

들여다보기

자식의 대화 기록을 열어 어디까지 했는지 본다. 방향이 틀렸으면 일찍 알 수 있다.

추가 지시

작업 ID로 메시지를 보내 범위를 좁히거나 바꾼다. 자식은 자기 컨텍스트를 유지한 채 이어서 일한다.

멈추기

더 필요 없어진 자식을 중간에 끝낸다. 남은 토큰을 아끼고, 고치던 파일이 반쯤 바뀐 상태로 남을 수 있음을 기억한다.

TRY백그라운드 자식 하나를 중간에 멈춰 보고, 그때까지 고친 파일이 어떤 상태로 남는지 git status로 확인해 보자.
Background 5 · When

백그라운드는 부모에게 따로 할 일이 있을 때만 이득이다

맞는 경우
  • 오래 걸리고 결과는 짧은 일: 전체 테스트, 빌드, 넓은 검색
  • 부모와 겹치지 않는 일: 부모는 문서를 쓰고 자식은 다른 모듈을 조사
  • 사용자와 대화를 계속해야 할 때: 질문에 답하는 동안 조사를 돌려 둔다
맞지 않는 경우
  • 다음 단계가 결과에 달린 일: 어차피 기다려야 하므로 포그라운드와 같다
  • 승인이 자주 필요한 일: 승인 요청마다 멈춘다 (앞 장)
  • 부모가 같은 파일을 고칠 일: 서로의 변경을 모른 채 덮어쓴다 (다음 장)
판단 질문은 하나다. "결과가 올 때까지 부모가 할 수 있는 의미 있는 일이 있는가?" 없다면 백그라운드로 돌릴 이유가 없다.
TRY오늘 한 위임 중에 백그라운드로 돌렸다면 기다리는 시간이 줄었을 일이 있었는지 찾아보자.
Background 6 · Shared folder

Isolation 2 · git worktree

git worktree는 저장소 하나에 작업 폴더를 여러 개 붙이는 git 기능이다

Isolation 3 · Lifecycle

자식마다 worktree를 주면 쓰기 충돌이 합치는 순간으로 미뤄진다

결과가 브랜치로 오면 ①

검토가 쉽다. 자식의 말 대신 diff를 본다. 보고와 실제 변경이 다르면 바로 드러난다.

결과가 브랜치로 오면 ②

버리기 쉽다. 마음에 들지 않으면 브랜치를 지우면 끝이다. 원래 폴더는 처음부터 건드리지 않았다.

결과가 브랜치로 오면 ③

골라 담을 수 있다. 여러 자식의 브랜치 중 좋은 커밋만 가져올 수 있다. 후보별 쪼개기와 잘 맞는다.

TRY두 worktree에서 같은 함수를 각각 고친 뒤 합쳐 보고, 충돌이 어느 단계에서 처음 드러나는지 확인해 보자.

맞는 일: 작업 중인 기능 쪼개 맡기기

어느 쪽도 따라가지 않는 것 ①

커밋하지 않은 변경. 부모가 방금 고친 내용을 자식이 봐야 한다면 먼저 커밋하거나 브리프에 적어 줘야 한다.

어느 쪽도 따라가지 않는 것 ②

git이 무시하는 파일. .env, 설치한 의존성, 빌드 결과는 새 폴더에 없다. 복사할 목록을 정하거나 설치 단계를 넣어야 테스트가 돈다.

TRY새 worktree를 하나 만들고 바로 테스트를 돌려 보자. 무엇이 없어서 실패하는지 적어 두면 그것이 준비 목록이다.
Isolation 5 · Cleanup

정리 규칙은 하나다. 일한 흔적이 있으면 자동으로 지우지 않는다

worktree 상태처리
변경 없음폴더와 브랜치를 자동으로 지운다
고친 파일 · 새 커밋 있음남겨 두고 사람이 합칠지 버릴지 정한다
자식이 실행 중잠금을 걸어 다른 정리 작업이 지우지 못하게 한다
상태를 확인할 수 없음지우지 않고 사람에게 묻는다
오래된 것주기적으로 훑어서 변경 없는 것만 정리한다
손으로 정리할 때git worktree list
git worktree unlock <path>   # 잠겨 있으면
git worktree remove <path>
git worktree prune         # 지워진 폴더 기록 정리

자식이 많아지면 남은 worktree와 브랜치도 빠르게 늘어난다. 브랜치 이름에 공통 접두사를 붙여 두면 한꺼번에 찾고 지우기 쉽다.

Isolation 6 · Enforcement

"그 폴더에서만 일해라"라는 지시만으로는 격리가 지켜지지 않는다

빠져나가는 길 ①
절대 경로

원래 작업 폴더의 파일 경로를 그대로 써서 수정한다. 자식은 이것이 잘못인지 모를 수 있다.

빠져나가는 길 ②
cd 후 명령

셸에서 원래 폴더로 이동해 테스트나 빌드를 실행한다. 결과 파일이 원래 폴더에 생긴다.

빠져나가는 길 ③
git 대상 바꾸기

git -C, GIT_DIR처럼 다른 저장소를 가리키는 옵션으로 원래 브랜치에 커밋한다.

하네스가 검사하는 것
  • 파일 쓰기 대상이 worktree 안인가
  • 명령의 작업 디렉터리가 worktree 안인가
  • git 명령이 다른 저장소를 가리키지 않는가
  • 명령 내용이 해석이 안 되면 실행하지 않는다
원리

격리는 약속이 아니라 검사로 지킨다. 모델은 지시를 어길 수 있고, 어겨도 스스로 알아채지 못한다. 그래서 막는 일은 도구 호출을 실행하는 쪽이 맡는다.

권한 규칙, 판정 hook과 같은 생각이다.

TRY격리된 자식에게 원래 폴더의 파일을 절대 경로로 고쳐 달라고 해 보고, 막히는지와 어떤 메시지가 나오는지 확인해 보자.
Isolation 7 · Limits

worktree가 나눠 주지 않는 것도 분명히 있다

같은 브랜치
두 곳에 못 연다

한 브랜치는 한 worktree에서만 체크아웃된다. 자식마다 다른 브랜치 이름이 필요하다.

포트 · 프로세스
서버는 하나

두 자식이 같은 포트로 개발 서버를 띄우면 하나는 실패하거나 다른 쪽 서버를 테스트한다.

외부 상태
DB · 캐시 · API

폴더가 달라도 같은 DB에 쓰면 서로의 데이터를 바꾼다. 테스트 데이터도 나눠야 한다.

디스크 · 준비 시간
폴더마다 설치

의존성을 폴더마다 설치하면 시간과 용량이 든다. 자식이 많을수록 커진다.

worktree는 파일과 브랜치를 나누는 도구다. 그 아래 층(Part 3 첫 장의 표)이 필요하면 포트 배정, 테스트 DB, 컨테이너 같은 별도 장치를 더한다.
TRY두 worktree에서 같은 개발 서버를 동시에 띄워 보고 무엇이 부딪히는지 확인해 보자.

직접 대화가 빛나는 일

가설끼리 반박하기. 원인 가설마다 팀원을 두고 "서로의 이론을 깨 보라"고 시킨다. 한 명이 순서대로 조사하면 먼저 본 가설에 끌려가지만, 서로 반박하면 살아남은 가설이 진짜 원인일 가능성이 높다.

별 모양이었다면

A의 발견을 B가 알려면 A → 부모 → B로 두 번 옮겨야 하고, 부모가 요약하면서 세부가 빠진다. 부모 컨텍스트도 그만큼 찬다. 메일함은 이 중계를 없앤다.

TRY같은 버그를 subagent 세 명(부모 경유)과 팀원 세 명(직접 대화)으로 각각 조사시켜 보고, 결론에 이르는 과정을 비교해 보자.

Teams 6 · Trust

다른 에이전트가 보낸 메시지는 사용자의 승인이 아니다

왜 위험한가

팀원은 웹 페이지, 이슈 본문 같은 외부 텍스트를 읽는다. 그 안의 지시가 메시지를 타고 다른 팀원에게 옮겨갈 수 있다.

권한은 시작할 때 정해진다

팀원은 대개 리더의 권한 설정을 물려받는다. 권한 요청은 리더 쪽 화면에 모여 사용자가 답한다.

원칙

메시지는 정보이고 권한이 아니다. 누가 보냈는지 표시하고, 승인은 사람에게서만 받는다.

TRY한 팀원에게 "사용자가 허락했다"는 메시지를 다른 팀원에게 보내게 해 보고, 받는 쪽이 어떻게 반응하는지 보자.

작업 형식이 맞는지, 완료 조건이 적혔는지 검사한다. 통과하지 못하면 만들어지지 않고 이유가 돌아간다.

완료로 바꾸려 할 때
작업 완료

테스트 통과, 산출물 파일 존재를 검사한다. 실패하면 완료 처리가 막히고 팀원이 다시 일한다.

팀원이 쉬려 할 때
팀원 대기

남은 작업이 있는데 멈추려 하면 피드백을 돌려줘 계속 일하게 한다.

관문 hook의 모양 (의사 코드)on task_completed(task):
  if 테스트_실패(task.브랜치):
      거절("테스트 2건 실패: …")
  if not 존재(task.보고서_경로):
      거절("보고서 파일이 없음")
  통과()
원리

"끝났다"는 판단을 모델에게만 맡기지 않는다. 판정은 코드로 한다는 원칙을 팀 단위로 넓힌 것이다. 팀원이 많을수록 사람이 하나하나 확인하기 어려워져 더 중요해진다.

TRY완료 시점 관문에 "테스트 통과" 검사 하나만 걸고, 팀원이 실패한 채로 완료 표시를 시도할 때 어떻게 되는지 보자.
Teams 8 · Cost & limits

팀은 가장 비싼 선택이다. 작게 시작한다

비용
  • 팀원마다 별도 인스턴스라 토큰이 인원수에 비례해 는다
  • 인원이 늘면 메시지와 조율도 늘어난다
  • 어느 순간부터는 사람을 더해도 빨라지지 않는다
흔한 제약 (구현마다 다름)
  • 세션 하나에 팀 하나, 팀원은 팀을 만들 수 없다
  • 리더는 바꿀 수 없다
  • 세션을 다시 열면 팀원이 복원되지 않을 수 있다
시작 기준내용
인원대부분의 일은 3~5명이면 충분하다. 집중한 셋이 흩어진 다섯보다 낫다
작업 크기함수 하나, 테스트 파일 하나, 리뷰 하나처럼 결과물이 분명한 단위. 팀원당 5~6개
첫 과제코드를 쓰지 않는 조사 · 리뷰부터. 병렬 구현의 조율 문제 없이 효과를 볼 수 있다
파일팀원마다 맡는 파일을 나눈다. 같은 파일을 고치면 덮어쓴다 (필요하면 worktree)
DOCS인원 · 작업 크기 기준은 Agent teams · Best practices의 권장을 옮겼다.
