자식 여럿을
함께 일하게 하려면

기본 subagent는 작은 일 하나를 맡기기에 충분합니다.
일이 커지면 시간, 대기, 충돌, 전달에서 한계가 드러납니다.
이 자료는 그 한계를 푸는 네 가지 확장이 무엇을 얻고
무엇을 대가로 치르는지, 그래서 언제 켜야 하는지를 다룹니다.

subagent를 쓰는 이유: 부모의 맥락을 깨끗하게 유지

지저분한 조사는 자식이 맡고, 부모는 결론만 받아 큰 흐름에 집중합니다. 자식에게는 역할에 맞는 지시와 도구만 줄 수 있습니다. 작은 일 하나를 떼어 맡기기에는 이것으로 충분합니다.

일이 커지면 드러나는 네 가지 한계

기본 subagent가 잘못 만들어진 것이 아니라, 작은 일에 맞춰진 것입니다. 맡길 일이 크고 많아지면 이 네 가지가 병목이 됩니다.

이 자료의 목표: 확장마다 언제 켤지 스스로 판단하기

무엇을 얻는가

각 확장이 기본 모델의 어느 한계를 푸는지 원리부터 이해합니다.

무엇을 대가로 치르는가

토큰, 어긋난 결과, 병합 충돌, 조율 부담처럼 확장마다 새로 생기는 문제와 대처법을 익힙니다.

언제 켜는가

가장 단순한 구성에서 시작해, 한계가 실제로 드러날 때만 필요한 확장을 더하는 기준을 세웁니다.

확장은 많이 켤수록 좋은 것이 아닙니다. 도구의 설정 이름은 자주 바뀌므로 본문은 원리만 다루고, 도구별 설정은 Appendix에 모았습니다.

네 가지 확장과 각각이 푸는 한계

1~3부는 같은 구조 안에서 실행 방식을, 4부는 구조 자체를 바꿉니다. 예시는 모두 쇼핑몰 장바구니 기능 하나로 이어집니다.

병렬 설계

여러 자식을 동시에 실행하는 방법 자체는 간단합니다. 이 부에서 다루는 것은 그다음입니다. 무엇을 기준으로 나누고, 비용을 얼마나 감수하고, 돌아온 결과를 어떻게 합칠지 정하는 일입니다.

1기본 복습2나누는 기준3시간과 토큰4결과 모으기

복습: 병렬 실행의 기본 규칙 세 가지

여기까지는 병렬을 쓸 수 있는 조건입니다. 이 부의 나머지는 병렬을 잘 쓰는 방법, 곧 어떻게 나누고, 비용을 얼마나 감수하고, 결과를 어떻게 합칠지를 다룹니다.

나누는 기준에 따라 달라지는 결과의 모양

영역별

파일이나 모듈 단위로 나눠 맡깁니다. 쓰기 충돌은 적지만, 경계에 걸친 문제는 놓치기 쉽습니다.

먼저 따질 것: 쓰기 범위

관점별

같은 대상을 서로 다른 기준으로 검토합니다. 한 명이 한 가지 기준만 보므로 빠뜨리는 부분이 줄어듭니다.

먼저 따질 것: 결과 합치기

가설별

원인 후보마다 한 명씩 배정합니다. 처음 찾은 그럴듯한 설명에 매달리지 않게 됩니다.

먼저 따질 것: 판정 기준

후보별

같은 문제를 서로 다른 방법으로 풉니다. 부모가 결과를 비교해 고르므로 품질은 좋지만, 비용이 많이 듭니다.

먼저 따질 것: 비용

병렬의 대가: 시간을 아끼는 대신 늘어나는 토큰

토큰은 세 군데에서 늘어납니다. 자식마다 다시 읽는 기본, 자식들이 각자 읽어서 생기는 겹치는 탐색, 그리고 부모가 보고를 읽고 합치는 모으기입니다.

병렬의 품질은 결과 모으기에서 결정

같은 반환 형식

모든 자식에게 결론 · 근거 · 미확인처럼 똑같은 칸을 지정해 줍니다.

큰 결과는 파일로

자세한 내용은 자식마다 다른 이름의 파일에 쓰고, 부모에게는 요약과 파일 경로만 전달합니다.

판정 기준을 미리

결론이 엇갈릴 때 무엇을 믿을지 미리 정해 둡니다. 예를 들면 재현 테스트가 있는 쪽을 믿는 식입니다.

백그라운드 실행

전체 테스트에 10분이 걸린다면, 부모는 그동안 꼭 멈춰 있어야 할까요? 백그라운드 위임을 쓰면 부모는 작업 ID만 먼저 받고 다른 일을 하다가, 결과를 나중에 알림으로 받습니다.

1기다리지 않는 위임2중간에 오는 알림3어긋난 결과4권한 요청5실행 중 관리6언제 쓰나

백그라운드 위임: 작업 ID만 받고 바로 복귀

도구 결과 자리에는 "시작함, 작업 ID t-17"만 먼저 들어옵니다. 그래서 부모는 자식의 결과를 모르는 상태에서 다음 판단을 내립니다.

결과가 돌아오는 방식: 부모 대화에 끼어드는 알림 메시지

기다리지 않는 사이 코드가 바뀌면 생기는 어긋난 결과

생기는 문제

자식은 자신이 읽은 시점의 코드를 기준으로 보고합니다. 부모가 결과를 짐작하고 먼저 진행했다면, 반대 결과가 왔을 때 작업을 되돌려야 합니다.

줄이는 방법

자식이 보고할 때 시작 시점의 커밋을 함께 적게 합니다. 부모는 알림을 받으면 그 사이에 무엇이 바뀌었는지부터 확인합니다.

백그라운드 자식의 권한 요청: 사용자에게 바로 물을 수 없는 문제

읽기 전용으로

쓰기 도구와 실행 도구를 빼서 승인이 필요 없게 만듭니다. 탐색과 리뷰에 적합합니다.

미리 허용

필요한 명령만 허용 목록에 넣고, 나머지는 자동으로 거절합니다.

시작 전에 묻기

자식을 실행하기 전에 필요한 권한을 한꺼번에 확인받습니다.

막히면 보고

거절된 지점을 결과에 적고 종료합니다. 남은 작업은 부모가 이어서 처리합니다.

실행 중인 자식에게 필요한 세 가지: 보기, 지시, 멈추기

① 들여다보기

자식의 기록을 열어 진행 상황을 확인합니다. 방향이 틀렸다면 일찍 알아챌 수 있습니다.

② 이어서 지시

작업 ID로 메시지를 보냅니다. 자식은 자신의 컨텍스트를 유지한 채 이어서 작업합니다.

③ 멈추기

필요 없어진 자식을 종료합니다. 다만 고치던 파일이 반쯤 바뀐 상태로 남을 수 있습니다.

worktree 격리

자식 둘이 같은 cart.py를 동시에 고치면 어떻게 될까요? worktree는 자식마다 별도의 작업 폴더와 브랜치를 주고, 결과도 브랜치 단위로 받게 합니다.

1같은 폴더 문제2격리의 층3git worktree4만들고 합치기5기준점과 준비물6정리 규칙7격리 검사8나누지 못하는 것

컨텍스트는 따로여도 파일은 하나

덮어쓰기

A가 B의 수정을 모르는 채로 저장합니다. 위 그림이 이 경우입니다.

반쯤 바뀐 상태

부모가 테스트하는 순간 A의 수정이 절반만 반영되어 있으면, 엉뚱한 곳을 의심하게 됩니다.

git 상태 섞임

스테이징 영역과 브랜치를 함께 쓰기 때문에, 한 명의 커밋에 다른 자식의 변경이 섞입니다.

격리의 층: 기본 subagent가 나누는 것은 대화뿐

어디까지 나눌지는 자식이 무엇을 건드리는지에 따라 정합니다. 읽기만 한다면 대화 분리로 충분하고, 파일을 쓴다면 worktree가, 서버를 띄운다면 그 아래 층까지 필요합니다.

git worktree: 저장소 하나에 작업 폴더 여러 개

# 새 브랜치로 작업 폴더 하나 더
git worktree add ../wt/fix-total -b agent-fix-total

# 붙어 있는 작업 폴더 목록
git worktree list

# 다 쓴 작업 폴더 떼기
git worktree remove ../wt/fix-total
저장소를 통째로 복사하는 것과 다른 점

기록(.git)을 복사하지 않으므로 빠르고 가볍습니다. 한쪽에서 만든 커밋이 다른 쪽에서도 바로 보이므로 합치기도 쉽습니다.

근거: git-scm.com/docs/git-worktree

worktree에서 충돌이 드러나는 시점: 합칠 때

결과가 브랜치로 오면 검토는 diff로, 버리기는 브랜치 삭제로, 골라 담기는 필요한 커밋만 가져오는 것으로 끝납니다. 다만 같은 줄을 둘이 고쳤다면 합칠 때 충돌하므로, 서로 다른 파일을 맡기는 원칙은 그대로 지켜야 합니다.

기준점에 따라 달라지는 자식이 보는 코드

새 폴더로 따라오는 것은 커밋된 파일뿐입니다. .gitignore 대상과 커밋하지 않은 수정은 빠지므로, 새 worktree에서 테스트를 한 번 돌려 보면 무엇을 준비해야 하는지 알 수 있습니다.

정리 규칙은 하나: 작업 흔적이 있으면 삭제 금지

git worktree list
git worktree unlock <path>
git worktree remove <path>
git worktree prune
git branch -D agent-...

자식이 많아지면 남는 폴더와 브랜치도 금방 늘어납니다. 브랜치 이름에 공통 접두사를 붙여 두면 한꺼번에 찾아서 지우기 쉽습니다.

격리를 지키는 수단: 지시가 아니라 검사

모델은 "그 폴더에서만 작업하라"는 지시를 어길 수 있고, 어겨도 스스로 알아채지 못합니다. 그래서 도구 호출을 실행하는 하네스가 쓰기 대상, 작업 디렉터리, git 대상을 직접 검사합니다.

worktree가 나누는 것은 파일과 브랜치까지

같은 브랜치

한 브랜치는 한 worktree에서만 열 수 있습니다. 그래서 자식마다 다른 브랜치 이름이 필요합니다.

포트와 프로세스

같은 포트로 개발 서버를 띄우면 하나는 실패하거나, 다른 자식의 서버를 테스트하게 됩니다.

외부 상태

폴더가 달라도 같은 DB를 쓰면 서로의 데이터를 바꿉니다. 테스트 데이터도 나눠야 합니다.

디스크와 준비 시간

폴더마다 의존성을 설치하므로 시간과 용량이 듭니다. 자식이 많을수록 부담이 커집니다.

그 아래 층까지 나누려면 포트 배정, 테스트용 DB, 컨테이너 같은 장치를 따로 더해야 합니다.

Agent Teams

1~3부에서는 부모가 가운데 있는 구조를 그대로 두고 실행 방식만 바꿨습니다. 리뷰 담당이 구현 담당에게 "여기 빠졌어"라고 직접 말하려면 구조부터 바뀌어야 합니다. 팀에서는 팀원끼리 메시지를 주고받고, 같은 작업 목록에서 스스로 일을 가져갑니다.

1별과 그물2네 가지 부품3공유 작업 목록4메일함5팀원의 맥락6메시지와 승인7품질 게이트8비용과 시작 기준

subagent는 별 모양, 팀은 그물 모양

일 나누기

subagent는 부모가 일을 전부 나눠 줍니다. 팀원은 공유 작업 목록에서 스스로 일을 가져갑니다.

수명

subagent는 일 하나를 끝내면 결과를 내고 종료됩니다. 팀원은 여러 작업을 이어서 맡는 독립 세션입니다.

비용

팀원마다 별도의 인스턴스이므로 토큰이 많이 듭니다. 결과만 필요하다면 subagent가 낫습니다.

팀의 구성: 리더, 작업 목록, 팀원, 메일함

작업 목록은 누가 무엇을 하는지를, 메일함은 새로 알게 된 내용을 전달합니다. 둘 다 리더의 대화 밖에 있으므로, 리더를 거치지 않고도 팀이 일을 진행할 수 있습니다.

공유 작업 목록: 일을 대화 밖에서 나누기

한 작업에 한 명

잠금을 걸어서 같은 작업을 두 명이 가져가지 않게 합니다.

의존 관계

"이 작업이 끝나야 시작"이라는 조건을 걸면 순서가 있는 일도 나눠 맡길 수 있습니다.

알려진 약점

팀원이 완료 표시를 잊으면 뒤의 작업이 계속 막힙니다. 그래서 실제 상태와 가끔 맞춰 봐야 합니다.

메일함: 팀원끼리 리더를 거치지 않고 대화

자동 전달

보낸 메시지는 받는 쪽에 자동으로 도착합니다.

이름으로 한 명씩

모두에게 알릴 때도 받는 사람마다 따로 보냅니다.

쉬면 알림

팀원이 일을 마치고 쉬면 리더에게 자동으로 알림이 갑니다.

팀이 가장 잘 맞는 쓰임은 가설끼리 반박하기입니다. 원인 가설마다 팀원을 두고 서로의 가설을 반박하게 하면, 끝까지 남은 가설이 진짜 원인일 가능성이 높습니다.

팀원이 아는 것은 첫 지시뿐

팀원은 리더의 대화를 볼 수 없습니다. 그래서 첫 지시에는 목표, 범위, 이미 아는 것, 완료 조건, 반환 형식에 더해 같이 일하는 사람까지 적어야 합니다. 예: "토큰 만료 로직은 builder가 수정하고 있으니, 바뀐 부분은 builder에게 직접 물어보세요."

다른 에이전트의 메시지 ≠ 사용자 승인

팀원은 웹 페이지나 이슈 본문 같은 외부 글도 읽습니다. 그 안에 숨은 지시가 메시지를 타고 퍼질 수 있으므로, 메시지는 정보로만 다루고 권한으로 여기지 않습니다. 권한 요청은 리더 화면에 모아서 사용자가 직접 판단합니다.

"끝났다"는 판정은 모델이 아니라 코드 검사로

게이트는 hook으로 구현합니다. 검사를 통과하지 못하면 작업이 만들어지지 않거나, 완료 처리가 막히거나, 팀원이 작업을 계속합니다. 팀원이 많아서 사람이 일일이 확인하기 어려울수록 더 중요해집니다.

인원

대부분 3~5명이면 충분합니다. 일정 인원을 넘으면 사람을 더해도 빨라지지 않습니다.

작업 크기

함수 하나, 테스트 파일 하나처럼 결과물이 분명한 단위로 나누고, 팀원당 5~6개를 맡깁니다.

첫 과제

코드를 쓰지 않는 조사와 리뷰부터 시작합니다. 구현을 맡길 때는 팀원마다 맡는 파일을 나눕니다.

흔한 제약

세션당 팀은 하나이고, 팀 안에 팀을 만들 수 없고, 리더를 바꿀 수 없습니다. 세션을 다시 열면 팀원이 복원되지 않을 수도 있습니다.

인원과 작업 크기 기준: Claude Code 문서 · Agent teams best practices

필요할 때만 한 단계씩

왼쪽부터 차례로 따져 보고, 처음으로 "아니오"가 나오는 칸의 바로 앞에서 멈춥니다. 오른쪽으로 갈수록 할 수 있는 일이 늘어나지만, 아래 빨간 글씨처럼 챙겨야 할 것도 함께 늘어납니다.

하나를 바꿀 때마다 얻는 것과 챙길 것이 함께

기능바뀌는 것얻는 것새로 챙길 것
병렬 실행한 번에 하나 → 여럿을 동시에시간나누는 기준, 토큰 비용, 같은 반환 형식, 판정 기준
백그라운드기다림 → 기다리지 않음기다리지 않음지난 결과 확인, 미리 정한 권한, 실행 중 관리
worktree 격리같은 폴더 → 자식마다 다른 폴더동시 쓰기기준점과 준비물, 정리 규칙, 하네스 검사, 포트와 DB
Agent Teams부모와 자식 → 리더와 팀원직접 대화작업 목록 상태, 같이 일하는 사람, 메시지 신뢰, 품질 게이트, 비용

네 기능은 모두 나누기라는 생각 위에 있습니다. 기본 subagent가 대화를 나눴다면, 이 네 기능은 시간, 기다림, 파일, 소통 경로까지 나눕니다.

병렬

같은 코드를 영역별로 한 번, 관점별로 한 번 나눠 리뷰를 맡기고 찾아낸 문제가 어떻게 다른지 비교

병렬

같은 일을 자식 하나와 셋으로 각각 실행해 총 토큰과 걸린 시간 비교

백그라운드

긴 테스트를 백그라운드로 맡기고 그동안 부모가 같은 파일 수정. 돌아온 결과가 최신 코드와 맞는지 확인

백그라운드

허용되지 않은 명령이 필요한 일을 맡기고, 승인 요청이 어디에 뜨는지 확인

격리

새 worktree에서 바로 테스트를 돌려 무엇이 없어서 실패하는지 기록. 그 목록이 곧 준비 목록

격리

팀

첫 지시에서 "같이 일하는 사람"을 빼고 팀을 만든 뒤, 팀원끼리 메시지를 주고받는지 확인

팀
