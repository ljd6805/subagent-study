Part 1 · Common

동작 메커니즘

Subagent 호출은 마법이 아니다. 부모 Agent Loop 안의 도구 호출 하나로 시작해서, 도구 결과 하나로 끝난다.

Mechanism 1

Subagent는 부모 입장에서
그냥 도구 호출 하나다

User → Parent Agent Loop
          │
          ├─ tool_use: read / grep / bash ...        (평범한 도구)
          │
          ├─ tool_use: task / Agent                  ← 위임 도구
          │      │
          │      └──▶ Child Agent Loop (새 컨텍스트에서 자체 loop)
          │                 ... tool_use ↔ result 반복 ...
          │           ◀── final message
          │
          └─ tool_result: "자식의 마지막 메시지"  → 부모 loop 계속

부모는 자식 내부의 수십 번 도구 호출을 보지 않는다. 받는 것은 tool_result 한 덩어리뿐이다.

📎 위임 도구 이름OpenCode task   Codex 사용자가 명시 요청하면 spawn (문서에 도구명 없음)   Claude Agent (구 Task)
Mechanism 2 · Lifecycle

수명주기는 다섯 단계로 같다

1 Spawn

부모가 위임 도구를 호출. 어떤 agent에게 무슨 지시를 줄지 인자로 넘긴다.

2 Assemble

Harness가 자식용 시스템 프롬프트·도구·모델을 조립하고 빈 대화를 만든다.

3 Loop

자식이 독립적으로 Agent Loop를 돈다. 자기 권한 안에서 읽고, 실행하고, 판단한다.

4 Return

도구 호출 없는 마지막 메시지가 나오면 종료. 그 텍스트가 부모의 tool_result가 된다.

5 Resume / Close

ID로 이어서 지시하거나, 닫아서 자원을 반납한다.

5단계의 이름은 도구마다 다르다. OpenCode는 child session으로 들어가서, Codex는 /agent로 스레드를 전환해서, Claude는 SendMessage로 이어서 지시한다.

🔍 직접 확인자식 세션 기록이 어디 남는지 찾아보자. Claude: ~/.claude/projects/…/subagents/agent-{id}.jsonl · OpenCode: child session (<Leader>+↓)
Mechanism 3 · Context boundary

격리의 핵심은 "무엇이 넘어가지 않는가"다

Parent 컨텍스트
시스템 프롬프트 (부모용)
사용자와의 대화 전체
이미 읽은 파일 30개
검색 결과, 시행착오
위임 지시 (브리프)
Child 컨텍스트 (새로 시작)
자식 전용 시스템 프롬프트
부모가 쓴 위임 지시 = 첫 user 메시지
부모의 대화 기록
부모가 읽은 파일 내용
부모의 중간 추론

→ 자식은 브리프에 쓰인 것만 안다. 브리프가 빈약하면 자식은 처음부터 다시 찾는다.

예외: fork부모 기록을 통째로 물려주는 모드도 있다. Claude 내장 fork agent가 대표적이다. 격리를 포기하는 대신 브리프가 필요 없다.
Mechanism 4 · Return

돌아오는 것은 마지막 메시지 한 덩어리뿐이다

부모가 받는 tool_result (개념 예시)
tool_result (subagent: explore)
결론: 결제 한도 검사는 src/pay/limits.py:42 에서만 수행.
근거: validate.py는 limits.check()를 호출만 함.
미확인: queue.py 재시도 경로는 보지 못함.
세 가지 결과
  • 사용자에게 바로 안 보인다. 부모가 다시 요약해서 전달한다.
  • 중간 과정은 사라진다. 자식이 근거를 결과에 안 적으면 부모는 검증할 수 없다.
  • 길면 다시 부모 예산을 먹는다. 요약이 짧아야 격리의 이득이 남는다.

그래서 결과는 "결론 · 근거 위치 · 미확인 사항" 형식을 브리프에서 미리 정해 두는 편이 좋다.

📎 공식 문서Claude: final report만 부모에 반환
Mechanism 5 · Parallel

한 턴에 여러 번 호출하면
병렬 fan-out이 된다

Parent (한 번의 응답에 위임 도구 3회)
  ├─ task(explore, "auth 모듈에서 토큰 검증 위치 찾기")   ─┐
  ├─ task(explore, "pay 모듈에서 한도 검사 위치 찾기")     ├─ 동시에 실행
  └─ task(explore, "order 모듈에서 재시도 정책 찾기")     ─┘
                          ↓ 세 개의 tool_result
Parent: 세 결과를 합쳐 하나의 답 작성 (gather)
잘 맞는 일

서로 독립적인 조사·탐색·리뷰. 결과끼리 의존이 없을수록 이득이 크다.

안 맞는 일

같은 파일을 동시에 고치는 일. 마지막에 쓴 쪽이 이기고, 서로의 변경을 모른다.

🔍 직접 확인Codex 내장 역할은 explorer(읽기 위주 탐색)와 worker(구현·수정)로 나뉜다. 병렬 쓰기는 작업자마다 담당 파일을 나눠 주는 것이 기본 해법이다.
Mechanism 6 · Limits

중첩과 동시 실행에는 상한이 있다

자식이 또 위임? (기본 깊이)동시 실행 상한조절 방법
OpenCode불가 · subagent_depth 기본 1명시 상한 없음 (한 메시지 다중 호출)subagent_depth: 2 + 자식 permission에 task 허용
Codex불가 · max_depth 기본 1 (root=0)max_threads 기본 6 (동시에 열린 스레드)[agents] 테이블
Claude가능 · 메인 아래 3단계까지20개CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH, …_MAX_CONCURRENT_SUBAGENTS

상한이 있는 이유는 비용과 통제다. 재귀 위임은 토큰을 기하급수로 쓰고, 누가 무엇을 했는지 추적하기 어려워진다.

Part 1 · Common

조립 원리

Harness는 정의 파일을 읽어 네 가지 재료로 자식을 조립한다. 정의 파일의 필드는 전부 이 재료 중 하나를 바꾸는 손잡이다.

Assembly 1

Subagent = 프롬프트 + 도구 + 모델 + 첫 메시지

① System prompt
정체성

정의 파일 본문. "너는 읽기 전용 리뷰어다…" 역할·절차·반환 형식.

② Tools / Permission
손발

쓸 수 있는 도구와 허용·확인·거부 규칙. 부모보다 좁게.

③ Model / Effort
두뇌 크기

역할에 맞는 모델과 추론 강도. 미지정이면 부모 것을 상속.

④ First message
이번 일

부모가 호출 시점에 쓰는 위임 지시. 정의 파일이 아니라 런타임에 정해진다.

①~③은 정의 시점(파일)에, ④는 호출 시점(부모의 판단)에 정해진다. 좋은 subagent는 둘 다 좋아야 한다.

추가 재료도구마다 더 얹을 수 있다: 프로젝트 지시문(CLAUDE.md/AGENTS.md), 미리 실을 skill, 전용 MCP 서버, 턴 상한, 영구 메모리 등. Part 2에서 다룬다.
Assembly 2 · Routing

부모가 보는 것은 이름과 description 목록뿐이다

부모의 위임 도구 설명에 실리는 내용 (개념도)
Available agents:
- explore: 코드베이스를 빠르게 검색하는 읽기 전용 agent
- reviewer: 변경 후 코드 품질을 검토. 코드 수정 직후 사용
- doc-writer: API 문서를 작성
(본문 프롬프트는 호출될 때만 로드)
Skill과 같은 원리

Skill이 name·description만 먼저 보이고 본문은 필요할 때 읽히듯, subagent도 description이 라우터 역할을 한다.

  • 언제 써야 하는지 적는다 ("코드 수정 직후")
  • 다른 agent와 겹치지 않게 쓴다
  • 너무 길면 모든 턴의 예산을 먹는다

자동 위임이 안 되거나 엉뚱한 agent가 불리면 프롬프트보다 description부터 고친다.

🔍 직접 확인Claude Code는 description 합계가 15,000 토큰을 넘으면 시작 시 경고한다. Claude는 "use proactively" 문구, OpenCode는 description 필수 필드로 같은 역할을 한다.

Declare 3 · Anatomy

좋은 정의 파일은 언제 · 무엇을 · 어떤 손으로 · 무엇을 돌려줄지가 선명하다

---
name: code-reviewer
description: 코드 변경 직후 품질과 버그를 검토한다. 수정은 하지 않는다.   # ← 언제 (라우터)
tools: Read, Grep, Glob, Bash   # ← 어떤 손으로
model: sonnet   # ← 두뇌 크기
---
너는 읽기 전용 코드 리뷰어다.   # ← 정체성
1. git diff로 변경 범위만 확인한다. 범위 밖 파일은 읽지 않는다.   # ← 무엇을 (절차)
2. 테스트는 실행할 수 있지만 코드는 절대 고치지 않는다.
3. 결과는 아래 형식으로만 반환한다.   # ← 무엇을 돌려줄지
   - 판정: PASS | FAIL
   - 문제: 파일:줄 — 한 줄 설명 (최대 10개)
   - 미확인: 보지 못한 것
🔍 직접 확인이 파일을 세 도구 포맷으로 옮겨 보자. OpenCode는 tools 대신 permission, Codex는 본문을 developer_instructions로 옮겨야 한다.

Operate 1 · Brief

브리프는 "맥락이 전혀 없는 동료"에게 쓰는 메모다

결과는 파일로, 요약은 짧게, 판정은 코드로

Subagent작업 수행

왜 파일인가

tool_result는 부모 예산을 먹는다. 큰 산출물은 파일에 두고 경로만 넘긴다. (SKILL 심화 ⑥ 산출물 약속)

왜 코드 판정인가

"완료했습니다"는 증거가 아니다. 자식의 자기 보고를 validator로 확인한다. (Harness: completion ≠ success)

Hook으로 강제

Claude의 SubagentStop hook은 검사 실패 시 decision:"block"으로 자식을 계속 일하게 할 수 있다.

Operate 3 · Patterns

자주 쓰이는 형태는 네 가지로 정리된다

① Explore
찾기만 맡긴다

읽기 전용 + 작은 모델. 검색 잔해는 자식 창에 남기고 위치만 받는다.

② Fan-out
나눠서 동시에

독립적인 조각을 병렬 위임하고 결과를 합친다.

③ Reviewer
오염 안 된 눈

작성 과정을 모르는 자식이 결과만 보고 판정한다. 독립 검증.

④ Orchestrator–Worker
순서는 부모, 일은 자식

부모는 목록·순서·PASS/FAIL만, 한 건씩 새 worker에게. (기존 OpenCode 가이드)

세 도구의 내장 agent가 이미 이 패턴이다. explore(①)와 general/worker(②④)는 세 도구 모두에 비슷한 이름으로 있다.

Operate 4 · Cost & anti-patterns

위임은 공짜가 아니다.
안 나누는 편이 나은 경우가 있다

비용 세 가지
  • 토큰: 자식마다 시스템 프롬프트·지시문을 새로 싣는다
  • 지연: 자식이 처음부터 맥락을 다시 모은다
  • 전달 손실: 요약이 정보를 깎는다. 근거 없는 결론은 검증 불가
안티패턴
  • 파일 하나 읽는 일을 위임 (호출 비용 > 이득)
  • 여러 자식이 같은 파일을 동시에 수정
  • 부모가 자식 결과를 전부 다시 읽음 (격리 무효)
  • 자식이 또 자식을 부르는 무한 분할

판단 기준: 자식이 쓸 컨텍스트가 부모가 받을 요약보다 훨씬 클 때 위임한다.

Part 2 · Tool-specific

OpenCode

특징: mode로 primary와 subagent를 같은 체계에서 정의하고, permission으로 위임 대상까지 통제한다. 자식은 child session으로 남아 직접 들어가 볼 수 있다.

OpenCode 1 · Modes

agent 하나가 mode에 따라
주인공도, 위임 대상도 된다

mode: primary
사용자가 직접 대화

Tab으로 전환. 내장: build(모든 도구), plan(수정·bash는 ask)

mode: subagent
위임받아 일함

내장: general(다단계 작업, 수정 가능, 병렬용), explore(읽기 전용 빠른 탐색)

mode: all (기본값)
둘 다

mode를 생략하면 all. 직접 쓸 수도, 위임할 수도 있다.

숨은 시스템 agent(compaction, title, summary)도 같은 체계로 돈다. 외부 문서·의존성을 조사하는 읽기 전용 subagent scout도 내장되어 있다.

🔍 직접 확인opencode agent list로 내 환경의 agent와 mode를 확인해 보자.

OpenCode 3 · Invoke & control

permission.task로 "누구에게 위임할 수 있는가"까지 정한다

자동 호출
primary agent가 subagent의 description을 보고
task 도구로 위임한다
사용자가 직접 부르기
@general 이 함수가 어디서 호출되는지 찾아줘
위임 대상 제한 (primary agent 설정)
"permission": { "task": {
  "*": "deny",
  "orchestrator-*": "allow",
  "code-reviewer": "ask"
}}
  • 마지막으로 매칭된 규칙이 이긴다
  • deny된 agent는 task 도구 설명에서 아예 사라진다
  • 사용자의 @mention은 규칙과 무관하게 동작
중첩subagent_depth 기본 1: primary는 subagent를 부를 수 있지만 subagent는 또 부를 수 없다. 2면 한 단계 더, 0이면 위임 전체 금지.

Codex

특징: 명시적으로 요청할 때만 위임한다. 자식은 agent 스레드로 열리고 /agent로 오가며, 역할은 TOML로 선언한다.

Codex 1 · Explicit spawn

Codex는 명시적으로 요청할 때만
자식 스레드를 띄운다

명시 요청"subagent로 나눠서 해줘"
→
스레드 생성역할: default · worker · explorer
→
병렬 실행max_threads 6
→
결과 취합하나의 답
자동 위임은 하지 않는다

"Codex only spawns subagents when you explicitly ask it to." description만 보고 알아서 위임하는 OpenCode·Claude와 가장 큰 차이다.

상한은 "열린 스레드" 수

agents.max_threads(기본 6)는 동시에 열려 있는 agent 스레드 수를 제한한다. 비활성 스레드의 승인 요청도 메인 화면에 올라온다.

🔍 직접 확인같은 일을 "나눠서 해줘" 없이 시켰을 때와 붙여서 시켰을 때, 스레드가 생기는지 /agent로 비교해 보자.
Codex 2 · Roles

역할은 TOML 파일 하나, 전역 한도는 config.toml의 [agents]

.codex/agents/reviewer.toml
name = "reviewer"
description = "Read-only code reviewer; use for PR review."
developer_instructions = """
Review for correctness and tests.
Never edit files. Return PASS/FAIL + file:line list.
"""
model_reasoning_effort = "high"
sandbox_mode = "read-only"
nickname_candidates = ["Ada", "Linus"]
~/.codex/config.toml
[agents]
max_threads = 6     # 동시 스레드
max_depth   = 1     # 중첩 깊이 (root = 0)
# job_max_runtime_seconds: CSV 일괄 작업용 (선택)

내장 역할: default(범용), worker(구현·수정), explorer(읽기 위주 탐색).

필드필수: name, description, developer_instructions · 선택: nickname_candidates, model, model_reasoning_effort, sandbox_mode, mcp_servers, skills.config. 생략한 값은 부모 세션에서 상속한다.
Codex 3 · Context & TUI

권한은 물려받고, 스레드는 /agent로 오간다

상속

"Subagents inherit your current sandbox policy." 자식을 띄울 때 부모 턴의 런타임 오버라이드도 다시 적용한다.

결과 회수

요청한 subagent들이 끝나면 메인 스레드가 결과를 모아 하나의 답으로 정리한다.

CLI

/agent로 활성 agent 스레드를 전환하고 진행 중인 스레드를 들여다본다. 비활성 스레드의 승인 요청도 올라온다.

Headless 조합

codex exec로 스크립트에서 Codex를 비대화형 작업자로 띄울 수 있다. 외부 오케스트레이터가 부모 역할.

AGENTS.md는 역할이 아니다

AGENTS.md는 프로젝트 지시문(최대 32KiB)이다. 역할 정의는 agents/*.toml로 한다.

Claude 4 · Context & hooks

자식은 CLAUDE.md는 받고, 부모 대화는 받지 않는다

자식이 받는 것
  • 자기 시스템 프롬프트 + 환경 정보
  • 부모가 쓴 위임 메시지
  • CLAUDE.md·AGENTS.md 계층 (Explore·Plan 제외)
  • git status 스냅샷, skills에 지정한 skill
받지 않는 것
  • 부모 대화 기록, 부모가 읽은 파일
  • 부모가 이미 호출한 skill, auto memory

돌아가는 것: 최종 보고 + agent ID. 보고 안의 지시문처럼 생긴 텍스트는 검사된다.

SubagentStart  입력: agent_id, agent_type        → additionalContext로 맥락 주입 (차단 불가)
SubagentStop   입력: last_assistant_message, agent_transcript_path …
               → decision: "block" + reason 이면 자식이 계속 일함 (검증 게이트)
