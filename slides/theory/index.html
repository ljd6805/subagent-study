Part 1 · Common

동작 메커니즘

Subagent 호출은 마법이 아니다. 부모 Agent Loop 안의 도구 호출 하나로 시작해서 도구 결과 하나로 끝난다.

1도구 호출 하나2수명주기 5단계3넘어가지 않는 것4마지막 메시지5한 번 따라가기6병렬 fan-out7깊이와 동시 실행 상한
Mechanism 1 · Tool call

Subagent는 부모 입장에서 그냥 도구 호출 하나다

부모 창에 남는 것은 호출 1번 + 결과 1개뿐이다. 자식이 수십 번 검색하고 읽어도 그 잔해는 자식 창에서 끝난다.
위임 도구 이름도구마다 이름만 다른 같은 도구다. OpenCode task   Claude Agent (예전 이름 Task)   Codex 문서에 이름 없음. 어떤 agent를 부를지는 이 도구의 인자로 넘긴다.
Mechanism 2 · Lifecycle

수명주기는 세 도구 모두 다섯 단계로 같다

부모가 위임 도구를 호출한다. 어떤 agent에게 무슨 지시를 줄지 인자로 넘긴다.

Harness가 자식용 시스템 프롬프트 · 도구 · 모델을 조립하고 빈 대화를 만든다.

자식이 독립적으로 Agent Loop를 돈다. 자기 권한 안에서 읽고, 실행하고, 판단한다.

도구 호출이 없는 마지막 메시지가 나오면 종료. 그 텍스트가 부모의 tool_result가 된다.

ID로 이어서 지시하거나, 닫아서 자원을 반납한다. 기록은 남아 사후 추적할 수 있다.

5단계를 다루는 법이어서 지시 · 들여다보기기록이 남는 곳
OpenCode자식이 child session으로 남아 TUI에서 직접 들어간다세션 목록 (부모 · 자식 트리)
Codex/agent로 활성 agent 스레드를 전환해 들여다본다agent 스레드
ClaudeSendMessage로 agent ID에 이어서 지시한다~/.claude/projects/…/subagents/agent-{id}.jsonl
TRY자식 세션 기록이 실제로 어디 남는지 세 도구에서 각각 찾아보자.
Mechanism 3 · Context boundary

격리의 핵심은 무엇이 넘어가지 않는가다

자식은 브리프에 쓰인 것만 안다. 부모가 아는 것을 적어 주지 않으면 자식은 처음부터 다시 찾는다.
예외 · fork부모 기록을 통째로 물려주는 모드도 있다. Claude 내장 fork agent가 대표적이다. 격리를 포기하는 대신 브리프가 필요 없다.
Mechanism 4 · Return

돌아오는 것은 마지막 메시지 한 덩어리뿐이다

tool_result (개념 예시)subagent: explore
결론: 결제 한도 검사는 src/pay/limits.py:42 에서만 수행.
근거: validate.py 는 limits.check() 를 호출만 함.
미확인: queue.py 재시도 경로는 보지 못함.
결과 ①

사용자에게 바로 보이지 않는다

부모가 다시 읽고 요약해서 전달한다. 자식 보고서는 부모를 위한 글이다.

결과 ②

중간 과정은 사라진다

자식이 근거를 결과에 적지 않으면 부모는 검증할 수 없다.

결과 ③

길면 다시 부모 예산을 먹는다

요약이 짧아야 격리의 이득이 남는다.

그래서 반환 형식 결론 · 근거 위치 · 미확인을 브리프에서 미리 정한다.
DOCSClaude: 자식의 final report만 부모에 반환
Mechanism 5 · Walk-through

위임 한 번을 처음부터 끝까지 따라가 보면

상황: "한도를 넘는 결제가 통과된다"는 버그 보고. 부모는 원인 조사를 explore 자식에게 맡긴다. (개념 예시)

#단계부모 창에 쌓이는 것자식 창에 쌓이는 것
1요청사용자 메시지 "한도 초과 결제가 통과돼"아직 없음
2고르기agent 목록의 description을 보고 explore 선택아직 없음
3위임task(explore, 브리프 5줄) 호출 1건자식 시스템 프롬프트 + 브리프
4자식 작업변화 없음 (기다림)grep 3회 · 파일 6개 읽기 · 막다른 길 2번 ← 무거운 부분
5반환tool_result 3줄: 결론 · 근거 · 미확인마지막 메시지 작성 후 종료
6계속3줄을 바탕으로 수정 계획을 세운다닫힘 (기록만 남음)
무거운 4단계가 통째로 자식 창에 있다. 부모가 얻은 것은 3단계의 호출과 5단계의 3줄뿐이다.
Mechanism 6 · Parallel

한 턴에 여러 번 호출하면 병렬 fan-out이 된다

잘 맞는 일

서로 독립적인 조사 · 탐색 · 리뷰

결과끼리 의존이 없을수록 이득이 크다. 지연은 가장 오래 걸리는 자식 하나로 줄어든다.

안 맞는 일

같은 파일을 동시에 고치기

마지막에 쓴 쪽이 이기고 서로의 변경을 모른다. 쓰기 병렬은 작업자마다 담당 파일을 나눠 준다.

TRYCodex 내장 역할은 explorer(읽기 위주 탐색)와 worker(구현 · 수정)로 나뉜다. 병렬로 맡길 때 어느 쪽을 고를지 생각해 보자.
Mechanism 7 · Limits

중첩 깊이와 동시 실행에는 상한이 있다

자식이 또 위임? (기본)동시 실행 상한조절
OpenCode불가 · subagent_depth 1명시 상한 없음subagent_depth: 2 + 자식 task 허용
Codex불가 · max_depth 1 (root=0)max_threads 6[agents] 테이블
Claude가능 · 3단계까지20개CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH 등 환경변수
상한이 있는 이유는 비용과 통제다. 재귀 위임은 토큰을 기하급수로 쓰고, 누가 무엇을 했는지 추적하기 어려워진다.

구성 요소

자식 agent는 네 가지 구성 요소로 만들어진다. 이 파트는 다섯 장으로, 첫 장에서 네 가지를 한눈에 보고 나머지 네 장에서 도구, 고르는 법, 권한, 모델을 하나씩 자세히 본다.

1네 가지 구성 요소2도구는 어디에 있나3description으로 고르기4권한 좁히기5모델이 정해지는 순서
Components 1

자식 agent = 지시문 + 도구 + 모델 + 첫 메시지

① 시스템 프롬프트

정의 파일 본문. 맡은 역할, 작업 순서, 결과를 돌려줄 형식을 적는다.

② 도구 · 권한

쓸 수 있는 도구와 허용 · 확인 · 거부 규칙. 부모보다 좁게 준다.

③ 모델 · 추론 강도

역할에 맞는 모델. 적지 않으면 부모의 모델을 그대로 쓴다.

④ 첫 메시지

부모가 호출할 때 쓰는 지시. 파일이 아니라 실행 중에 정해진다.

추가 구성도구에 따라 더 넣을 수 있다: 프로젝트 지시문(CLAUDE.md · AGENTS.md), 미리 불러올 skill, 전용 MCP 서버, 턴 상한, 영구 메모리. Part 2에서 다룬다.

Components 2 · Routing

부모는 이름과 description만 보고 누구에게 맡길지 고른다

부모가 보는 위임 도구 설명 (개념도)
explore — 코드베이스를 빠르게 검색하는 읽기 전용 agent
reviewer — 코드 수정 직후 품질을 검토한다. 수정은 하지 않는다 선택됨
doc-writer — API 문서를 작성한다

요청: "방금 고친 결제 코드 검토해줘" → 부모는 "수정 직후 · 검토"가 적힌 reviewer를 고른다.
Skill과 같은 방식

Skill이 name · description만 먼저 보이고 본문은 필요할 때 읽히듯, subagent도 description으로 선택된다.

description 잘 쓰는 법
  • 언제 쓰는지 적는다 ("코드 수정 직후")
  • 다른 agent와 겹치지 않게 쓴다
  • 짧게 쓴다. 목록은 매 턴 부모 예산을 먹는다
엉뚱한 agent가 불리면 본문보다 description부터 고친다.
TRYClaude Code는 description 합계가 15,000 토큰을 넘으면 시작할 때 경고한다. "use proactively" 문구가 자동 위임 빈도를 바꾸는지도 보자.

선언 방법

세 도구 모두 파일 하나 = agent 하나다. 위치와 형식만 다르고, 들어가는 필드는 거의 일대일로 대응한다.

1어디에 두나2이름이 겹치면3필드 대응표4정의 파일 해부5같은 agent, 세 가지 형식
Declare 1 · Where

프로젝트에 두면 팀 공용, 홈에 두면 나만 쓰는 agent

OpenCode 
my-repo/
├─ .opencode/agents/
│   └─ review.md      # 이름 = 파일명
└─ opencode.json     # "agent": {…}

~/.config/opencode/
└─ agents/           # 개인

Markdown + YAML 또는 JSON. 파일명이 이름이 된다.

Codex 
my-repo/
└─ .codex/agents/
    └─ reviewer.toml  # name 필드

~/.codex/
├─ agents/           # 개인
└─ config.toml       # [agents.이름]

TOML. 이름은 name 필드로 정한다.

Claude Code 
my-repo/
└─ .claude/agents/
    └─ reviewer.md    # name 필드

~/.claude/
└─ agents/           # 개인

claude --agents '{…}' # 이번 세션만

Markdown + YAML. 이름은 name 필드로 정한다.

같은 이름의 agent가 여러 곳에 있을 때 무엇이 쓰이는지는 도구마다 다르다. 다음 장에서 순서를 정확히 본다.

Part 1 · Common

운용 원리

정의 파일이 좋아도 브리프(첫 메시지)와 반환 약속이 나쁘면 위임은 실패한다.

1브리프 쓰는 법2결과 받는 법3네 가지 패턴4위임할까, 직접 할까5비용과 피할 패턴
Operate 1 · Brief

브리프는 맥락을 전혀 모르는 동료에게 쓰는 메모다

Before
"결제 쪽 버그 좀 찾아줘"
  • 어떤 버그? 증상이 없다
  • 어디까지? 리포 전체를 뒤진다
  • 언제 멈추지? 끝이 없다
  • 무엇을 돌려주지? 장문 보고서가 온다
After · 다섯 칸
목표한도 초과 결제가 통과되는 원인 찾기 범위src/pay/ 만. 수정 금지 알려진 것limits.py:42 에서 검사한다 완료 조건원인 후보 1~3개 + 근거 줄번호 반환 형식결론 / 근거 / 미확인
알려진 것 칸이 특히 중요하다. 부모가 이미 아는 것을 안 적으면 자식은 그것을 다시 비용을 들여 알아낸다.
Operate 2 · Return contract

결과는 파일로, 요약은 짧게, 판정은 코드로

왜 파일인가

부모 예산을 지킨다

tool_result는 부모 창에 쌓인다. 큰 산출물은 파일에 두고 경로만 넘긴다. (SKILL 심화 ⑥ 산출물 약속)

왜 코드 판정인가

"완료했습니다"는 증거가 아니다

자식의 자기 보고를 validator로 확인한다. (Harness: 완료 ≠ 성공)

Hook으로 강제

통과 전에는 못 끝낸다

Claude의 SubagentStop hook은 검사가 실패하면 decision: "block"으로 자식이 계속 일하게 한다.

output/result.json · 자식이 쓴다{

Operate 3 · Patterns

자주 쓰는 형태는 네 가지로 정리된다

① Explore

찾기만 맡긴다

읽기 전용 + 작은 모델. 검색 잔해는 자식 창에 두고 위치만 받는다.

② Fan-out

나눠서 동시에

독립적인 조각을 병렬로 맡기고 결과를 합친다.

③ Reviewer

선입견 없는 검토

작성 과정을 모르는 자식이 결과만 보고 판정한다. 독립 검증.

④ Orchestrator–Worker

순서는 부모, 일은 자식

부모는 목록 · 순서 · PASS/FAIL만 관리하고 한 건씩 새 worker에게 맡긴다.

세 도구의 내장 agent가 이미 이 패턴이다. explore(①)와 general / worker(②④)는 세 도구 모두에 비슷한 이름으로 있다.
Operate 4 · Decide

위임할까, 직접 할까: 네 가지 질문으로 정한다

기준 한 줄자식이 쓸 컨텍스트가 부모가 받을 요약보다 훨씬 클 때 위임한다.
Operate 5 · Cost & anti-patterns

위임은 공짜가 아니다. 나누지 않는 편이 나은 경우가 있다

비용 ① 토큰

자식마다 시스템 프롬프트와 프로젝트 지시문을 새로 싣는다. 자식 5개면 5번 싣는다.

비용 ② 시간

자식은 맥락 없이 시작해 처음부터 다시 모은다.

비용 ③ 전달 손실

요약이 정보를 깎는다. 근거 없는 결론은 부모가 검증할 수 없다.

피해야 할 패턴
  • 파일 하나 읽는 일을 위임한다 (호출 비용 > 이득)
  • 여러 자식이 같은 파일을 동시에 고친다
  • 부모가 자식 결과를 전부 다시 읽는다 (격리가 무의미)
  • 자식이 또 자식을 부르는 무한 분할
  • description이 겹치는 agent를 여러 개 둔다 (엉뚱한 선택)

Codex 1 · Explicit spawn

Codex는 명시적으로 요청할 때만 자식 스레드를 띄운다

자동 위임을 하지 않는다

"Codex only spawns subagents when you explicitly ask it to." description만 보고 알아서 위임하는 OpenCode · Claude와 가장 큰 차이다.

상한은 열린 스레드 수

agents.max_threads(기본 6)는 동시에 열려 있는 agent 스레드 수를 제한한다. 비활성 스레드의 승인 요청도 메인 화면에 올라온다.

TRY같은 일을 "나눠서 해줘" 없이 시킬 때와 붙여서 시킬 때, 스레드가 생기는지 /agent로 비교해 보자.

Claude 4 · Context & hooks

자식은 CLAUDE.md는 받고, 부모 대화는 받지 않는다

자식이 받는 것
  • 자기 시스템 프롬프트 + 환경 정보
  • 부모가 쓴 위임 메시지
  • CLAUDE.md · AGENTS.md 계층 (Explore · Plan 제외)
  • git status 스냅샷, skills에 지정한 skill
받지 않는 것
  • 부모 대화 기록, 부모가 읽은 파일
  • 부모가 이미 호출한 skill, auto memory

돌려주는 것: 최종 보고 + agent ID. 보고 안에 지시문처럼 생긴 텍스트는 검사된다.

SubagentStop을 검사 관문으로 쓰면, 운용 원리에서 본 "판정은 코드로"를 도구 차원에서 강제할 수 있다.
